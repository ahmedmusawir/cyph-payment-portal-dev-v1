### 1. Root cause and recovery behaviour

**Root cause** (`src/server/webhook.ts` at `2bb13b9`):
- A supported event with no mapping was finished as `ignored` and answered 200, so a missing mapping was treated as foreign and nothing retried.
- The duplicate check treated `ignored` as final.
- A subscription event that found its operation busy was finished as `processed`.

Two related defects were found during the repair and fixed:
- A failure write could overwrite a row that a concurrent delivery had already processed.
- A completion event whose payment was not yet settled was processed.

**Now:**
- **Acknowledged only when finished.** An event answers 2xx only when it is `processed`, or `ignored` for a proven reason: unsupported type, foreign object, another environment's object, or an invoice with no subscription.
- **Unfinished stays visible.** No mapping yet, a busy operation and unsettled payment stay `failed` with the reason and answer 503; provider or database errors answer 500.
- **Ownership is decided by trusted evidence:**
  1. this database's mappings;
  2. otherwise the application's marker on the object as Stripe returns it to our key (checkout now also writes `apbm_db`).

  A missing mapping alone is never treated as foreign. The marker never provisions anything.
- **Duplicates.** A duplicate of an unfinished event is processed again; only a duplicate of a finished event answers `duplicate`.
- **Recovery.** `operator-reconcile.mjs --list` and `--event <evt_ID>` re-run one exact recorded event through the same idempotent path. An audit record is written before any final row changes, and the row keeps `recovered_from_…`. Nothing is reset or deleted.
- **DEV today:** 2 events, both processed through the mirror; 0 suspect, 0 unfinished.

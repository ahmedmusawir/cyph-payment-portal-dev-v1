# Invitations, admin and membership

OwedBook owns staff UI and user-authorized invitation/membership RPCs. User cookie-bound RPCs rederive authority from auth.uid; no service key substitutes for a user's authorization. A narrow server-only invitation identity/mail module may use admin access only after scoped inviter check. Maintain explicit bundle/import boundary tests. Stripe remains Portal-only.

Create invitation first with lower-case recipient email, store/account/role/actor, expiry, intended incumbent and disposition. Unique live invitation per store/email and one live admin invitation per store; 7-day expiry. Maximum five dispatch attempts total, minimum 60 seconds between resend claims. Record every actual attempt, including refusals/timeouts. New invitee uses admin identity creation without public signup; existing identity reused with no password reset. No role granted at send. Validate provider disabled-signup behavior on controlled SCRATCH identity before its first real new-invitee send. Proven 007A flow is precedent, not new independent Auth evidence.

Email is the existing Auth sign-in flow with explicit confirm button, then OwedBook /invitations. Sign-in-link expiry and 7-day invitation expiry are distinct. GET may display but never verify OTP, accept invite, grant membership or consume an invitation. Accept only explicit same-origin/CSRF-bound POST with current auth-server-verified session and verified recipient identity/email. Wrong signed-in person must deliberately switch; do not disclose a full other recipient address. Revoke/decline/expire removes pending authority, even if sign-in link itself still logs in. Cross-account recipient may join; no billing rights follow.

Owner may invite/replace admin or invite/remove members in own stores; store admin may manage members of assigned stores only; member/foreign/signed-out cannot manage. Atomic acceptance locks store+invite, rechecks state/expiry/recipient/incumbent; if incumbent changed since issue, reject stale invitation and require reissue. Demote old admin to member unless removal selected; insert/upgrade new admin in same transaction. Owner remains platform member and retains owner rights even if store membership demoted. Never zero/two effective admins. Removal cannot delete effective admin; owner recovers via replacement, support audited action when owner cannot act.

Every new grant/write checks active store and account writable in SQL as well as app. During grace normal access with banner; read-only denies new grants/ordinary mutations but permits authorized revocation/revoke-invite (access reduction), owner billing recovery and audited support recovery. Revocation takes effect on next app/data authorization, including existing JWT requests; identity session may remain valid until expiry. Cover owner-role bypass, definer RPCs and direct table privileges, not only membership deletion. Refresh stale store navigation on denial.

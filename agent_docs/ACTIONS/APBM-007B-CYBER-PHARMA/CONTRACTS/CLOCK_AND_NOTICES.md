# Grace clock and billing notices

## O-1 with production-excluded time seam

Only isolated SCRATCH fixtures may use simulated time. Existing DEV accounts always use real server time, regardless of non-null stale clock fields. SQL deployment context stores the verified project identity; only SCRATCH identity may enable test context. Context is service-only, account/run/clock-bound and separate from user tables. SQL billing_now must ignore simulated time unless that verified SCRATCH context is enabled; disabling context returns now() even if old test timestamps remain. Browser input/headers and a boolean supplied to an arbitrary RPC never enable it. Direct authenticated/anon calls to enable/set clock are denied. Runtime ALLOW_TEST_CLOCK additionally requires APP_ENV=local and SCRATCH URLs; mismatch fails startup/fixture invocation. Staging/production omit flag, and boot refuses a SCRATCH test context under their configuration.

Record explicit disable/deactivate in fixture cleanup before switching application flag off. Required negatives: context disabled with non-null old clock time; forged user flag/header; direct SQL/RPC user call; staged configuration with flag off; DEV deployment identity even with injected non-null clock values. No production-use claim based merely on “we will not set the flag”.

Stripe clock owns provider chronology; mirror frozen time only from authoritative clock retrieval. Grace start is the relevant failed-renewal invoice timestamp in that timeline, not worker processing time; duplicate/delayed events cannot shift it. Real account time remains unchanged. Internal assert_account_writable uses the same account timeline as access state. Fixture creation, sync, run and disable are implemented by scripts/apbm007b/testclock.mjs behind operator gate and hard budgets.

CP-2 verifies provider clock, timestamp mapping and the SQL exclusion boundary before the lifecycle build. Fallback is an external operator-owned standalone Stripe clock driver plus a private SCRATCH-only time-context setter with the same SQL guard; all application production endpoints remain unaware of fixture creation. This is a fixed fallback, not permission to patch global now(), forge old failure rows, replace live events with mocks or weaken the clock-negative proof. If neither driver can produce real provider chronology, block O-1 and report the exact capability failure; other safe work continues, no O-1 PASS.

Journey: one account/two stores → set failing card and renewal advance → normal access/banner for seven days → day-five warning → read-only for owner/admin/member; SQL new writes denied, owner billing reachable → working card/paying same delinquent invoice restores access → replay old failure has no effect. Cancel/undo/retry never reset grace. Within this SAME clock campaign do PE-09 Add Store well inside a paid period: incremental invoice less than 4900 cents and equals bound quote; also ordinary and APA variants. No separate third pre-E2 clock campaign is required.

## O-2 single sender

Portal src/server/billingNotices.ts alone sends billing notices using Resend HTTPS API and server-only RESEND_API_KEY. Sender: Cyber Pharma <no-reply@cyberizedev.com>, the supplied earlier verified sender; validate private key can send from it before first allowed dispatch. Preserve current Auth SMTP settings for sign-in/invitation flow. No billing-notice fallback through sign-in email.

Kinds: renewal_payment_failed at first unpaid subscription_cycle failure; renewal_read_only_warning at grace_start+5 days (48 hours before read-only). Owner Auth email only; link to authenticated Portal billing. Include truthful deadline/status; amount only if invoice-derived. Do not disclose another tenant or invent legal copy. Unique durable (invoice_id, notice_kind), persisted payload fingerprint, attempt/receipt/status. Suppress legacy pending renewal_reminder rows with recorded reason; preserve history.

Runtime mail guard defaults ON. MAIL_ALLOWLIST comma-separated exact normalized addresses; absent/empty means deny all, not allow all. No wildcard/production bypass in E2; MAIL_GUARD=off is not authorized. Guard applies to new notice and invitation dispatch adapters; Auth preflight test cast is also checked before calling sign-in send. Validate allowed and blocked address controls before spending any dispatch budget. Blocked local validation consumes no provider dispatch but is logged separately. Every actual attempted send counts, including failed/uncertain requests.

Resend Idempotency-Key = notice_kind/invoice_id, stable payload, durable claim under account+notice lock. Retry definite refusal with bounded backoff, maximum five attempts and inside the key-retention window; stop automatic reissue before 23 hours from first dispatch. Unknown timeout after that horizon is attention, never a new key/send. Provider idempotency is time-bounded and is not permanent deduplication. Revalidate paid/grace state immediately before serialized dispatch and before each retry; recovery and notice claiming share the account transition lock. Record dispatch linearization so recovery committed first suppresses send. Email already accepted in flight can arrive after recovery; do not describe receipt time as controllable.

POST /api/internal/jobs/run handles both due notices (15-minute cadence sufficient) and operation expiry (one-minute cadence). Local owned runner every minute; staging Cloud Scheduler definition authenticated, minute cadence. No public job token or anonymous invocation. SQL notifies/claims are service-only. Failing to send does not roll back or acknowledge lost billing event work; durable retry responsibility must be recorded. Inbox observation is required, not just a provider message ID.

# Paid Add Store and quantity contract

## Sources of authority

Stripe reads establish payment/object state; SQL owns account/role/NPI authority and transitions. Browser values never select customer, subscription, quantity, amount, account or payment result. Portal alone imports Stripe. Existing subscription mapping and catalogue are reused; new Add Store never creates another subscription or billing customer for the account.

## Incremental charge — preserves earned APA discount

Do NOT rerate existing stores with default quantity-change proration. At quote time retrieve active subscription, item, price and its authoritative current period [s,e]. Compute a positive integer-cent amount `floor((4900*(e-t)+((e-s)//2))/(e-s))`, with integer arithmetic, t clamped to [s,e]; equivalent half-up rounding of the new store's remaining-period price. Derive 4900 from the guarded second catalogue tier, not a browser constant. Bind period, calculation inputs and rounding. Reject invalid/nonpositive intervals. Define one named constant STRIPE_MIN_CHARGE_USD_CENTS = 50. If the computed amount is below 50 cents, refuse the quote and the confirmation with a plain message that the store can be added after renewal. No invoice is created and no customer balance is created. This refusal replaces the 90-minute rule wherever it is stricter; do not charge a full $49 for a half-period add. Tax/credit/customer-discount configurations outside the tested no-balance USD fixture return `billing_configuration_attention` without mutation; do not silently spend credit, alter tax or recover an old discount. No new promotion is entered in Add Store; an already-earned first-store discount is preserved.

15-minute stored quote includes store/NPI, canonical pharmacy identity if known, account/customer/subscription/item/price, period, billable quantity before/after, currency, cents, discount explanation, computed timestamp, expiry and terms version. Confirmation accepts quote ID, consent flags and client intent key only; re-read/validate binding under one account billing-operation lock. Display next renewal total (9900 + 4900*(billable_count_after-1)), amount now and fixed payment deadline; require explicit consent. New key for the same unresolved intent resumes; conflicting store details return conflict rather than charge a different intent.

## Separate invoice saga — all adds, including APA

1. Commit durable operation/intent and NPI hold first; one unresolved billing operation per account. Save intended provider calls/parameters and immutable consent.
2. Create a draft standalone invoice for the existing customer, no subscription association, collection_method charge_automatically, auto_advance=false, pending_invoice_items_behavior=exclude, discounts empty; operation/run/environment metadata. Save unique invoice→operation mapping before any collection. Create exactly one amount/currency invoice item attached explicitly to that invoice, discountable=false. No unrelated pending invoice items.
3. Retrieve draft and validate line amount, due amount, currency, customer, metadata and zero balance against quote. Unexpected discount/credit/tax or duplicate line → attention, no payment. Finalize with auto_advance=false. Verify these pinned-version calls in CP-1.
4. Attempt payment once within the consent window using that invoice. On required action/card change, owner uses Stripe-hosted invoice page. Never call sendInvoice or rely on automatic reminder/collection. Store hosted URL server-side as sensitive capability; deliver only to authenticated owner with no-store/referrer controls; never export full URL. App return triggers reconciliation, not grant.
5. On authoritative paid invoice with exact operation/currency/amount and within the window, recheck unchanged subscription period/customer/price, set the existing item's absolute quantity to operation.target_quantity with proration_behavior=none and unchanged billing anchor. Verify result. Atomic SQL activation then inserts active ownership record and owner's admin membership, consumes NPI hold and marks activated. Until this final transaction no business row or membership grants access. Network faults preserve `paid_pending_activation`; never release NPI or charge again.

States: quoted (separate quote), payment_setup, payment_pending, paid_pending_activation, activated, cancel_requested, expired_unpaid, attention, closed_refunded_externally (terminal). Unresolved states hold the account-operation slot. Every state transition is row-locked and version/fencing-token checked; provider updates use absolute desired state, never read-plus-increment retries. Lease expiration does not allow an old worker to finalize writes; final SQL independently verifies operation and identity. Do not copy the pre-repair per-process lease owner.

## Expiry and late payment

Consent deadline is 30 minutes after confirm, no later than period_end minus 60 minutes; confirm refused within last 90 minutes. Show deadline before payment. `POST /api/internal/jobs/run` executes expiry every minute locally under owned runner and at staging scheduler. Reconcile on owner polling, signed events and operator recovery too. Merely closing the tab is not abandonment.

At deadline/explicit abandon, persist closing intent under lock, retrieve invoice, void if still open and verify terminal provider state. Never mark unpaid from missing reference, expiry alone or uncollectible alone; require void/zero-paid and no successful payment. If payment races void or arrives after deadline/abandon: preserve exact paid operation, enter attention, do not automatically activate or charge again, no automatic refund. Show payment-received/support state. Operator may resume the original operation only after recorded owner reconfirmation and fresh period/quantity disposition; no arbitrary amount/time override. Late-payment and job-crash cases are mandatory tests.

## Historical reconciliation and webhook routing

Every money call has persisted intent, stable operation-derived key and provider outcome. Invoice mapping is unique; retain all attempt/invoice IDs in a mapping/history table if an operation has more than one provider artifact. Invoice creation is the only stage that may lack ID after reply loss: enumerate the customer's invoices over the bounded operation creation interval and exact metadata/customer/currency/amount, across all pages. Reuse only an unambiguous artifact. After provider key retention or incomplete history, NEVER interpret no current pending update/latest invoice as proof of no prior charge. Attention blocks reissue; use audited recovery, not a new charge. Paid invoice and operation history remain authoritative after renewal/void/latest-invoice changes.

Webhook order: verify signature/test/account → durable event receipt → operation invoice lookup and metadata reconciliation → Add Store saga; first-store subscription_create retains 007A path; renewal grace only subscription_cycle. Standalone manual invoice with unknown mapping remains retryable until trusted foreign proof; no silent 2xx loss. Metadata stamped after payment is never the only mapping. A healthy subscription with latest invoice open/void never enters grace on that fact alone. Preserve unfinished-event non-2xx and exact-ID recovery. No activation solely on pending_update_applied; synchronous payment, signed invoice.paid and recovery all converge on authoritative invoice/state.

## Quantity/access accounting

Billable count excludes scheduled removals immediately; still-paid access continues until stored cutoff. Absolute subscription quantity equals billable count plus any durably recorded paid transition being completed; stable states must agree. Never infer unnamed store access from quantity. Add after a scheduled removal pays only the new store fraction; undo restores a still-paid store without charge. Same account-operation lock serializes add/remove/undo/transfer. Test N=3→schedule one→add one→undo plus renewal-boundary races. Conflicting period/quantity after payment is attention, never a guessed second update.

No provider mechanism fallback is silently selected. CP-1 has fully specified success criteria and stop/resume behavior in EXECUTION_PLAN.md; if this mechanism fails, stop affected billing and return one bounded contract amendment while unrelated safe work continues.

## BP-02 common period-boundary window

Use one shared predicate for Add Store, removal scheduling and removal undo: refuse when remaining time is within90minutes OR the computed hypothetical added-store remaining-period amount is below STRIPE_MIN_CHARGE_USD_CENTS. Compute only; do not create a provider invoice to decide this window. Bind each mutation to the retrieved subscription/item period. After quantity update re-read; changed period enters attention and no ownership is finalized or reactivated using stale dates. No store may be left active in a period whose renewal invoice excluded it, or billed beyond its effective cutoff without an explicit attention disposition and corrective provider evidence. Preserve requested/bound dates and provider invoice references; never silently shift cutoff or apply the old quote. Show attention/recovery honestly.

## BP-04 paid operation terminal closure

If a paid store operation will not be activated, only owner-reconfirmed activation under the existing reconciliation rules OR store-operation-close on authoritative provider proof of full refund/credit can resolve it. Closing never issues a refund or activates. Fully refunded means exact operation invoice/payment net collected amount returned, with provider reference, currency and no uncovered paid balance; a mere customer credit-balance entry or unverified note is insufficient. Fully credited invoice evidence must extinguish the whole operation liability, not merely an unrelated adjustment. Refuse partial/ambiguous proof. On valid proof atomically set closed_refunded_externally, retain payment/refund/audit history, and release only that operation's NPI hold and account slot. Idempotent repeated close returns same receipt. No app refund feature is introduced.
